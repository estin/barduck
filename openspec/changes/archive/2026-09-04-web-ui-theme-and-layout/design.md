## Context

The web dashboard (`src/web.rs`) is server-rendered by a topcoat shard; there is no client-side framework, only plain `<script>` tags (see `CONNECTION_SCRIPT`, `FAVICON_SCRIPT`). `assets/styles.css` already defines a complete light/dark token pair (`:root` / `.dark`, toggled by a `dark` class on an ancestor — see the file's own header comment) but nothing ever applies that class today. Panel/pane cards are built from the vendored `topcoat` `card`/`card_header`/`card_title`/`card_content`/`card_footer` components (`src/components/card.rs`, tracked by content hash in `components.toml`); `card` is used nowhere else in this app (only in `panels_grid`, confirmed by a full-repo grep), so it is safe to treat as project-owned rather than a shared primitive other pages depend on. The panel grid (`panels_grid` in `src/web.rs`) places every cell with explicit `grid-row`/`grid-column` inline styles and forces the grid's own `grid-template-columns` to the layout's exact column count via an inline style — this inline value has no way to vary by viewport, which is the root cause of the mobile-layout problem. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- Ship all four changes as presentation-only work: no config schema, TUI, CLI, or database changes.
- Keep the fix confined to `assets/styles.css` and `src/web.rs` (plus the vendored `card.rs`, which this app owns).

**Non-Goals:**
- No user-configurable accent color or additional themes beyond the existing light/dark pair.
- No redesign of the grid's explicit row/column placement model for desktop/tablet widths — only the narrow-viewport case collapses to a single column.
- No change to `card_header`/`card_title` as generic vendored primitives; they simply go unused by `panels_grid` after this change (harmless — they're `pub`, so rustc's `dead_code` lint doesn't fire on unreachable-private-item grounds, and they remain available for any future page that wants a plain header-row card).

## Decisions

**Theme: a server-known cookie, not client-only `localStorage`.** Revised mid-implementation: the original plan (a blocking bootstrap script reading `localStorage`) was replaced because it can't satisfy "the backend knows the user's theme" — the server has no access to `localStorage`. Instead, `POST /api/theme` (`src/api.rs`, using `topcoat::cookie`) writes a `bd_theme` cookie, and every page (`dashboard()`, `source_logs()`) reads it via `theme_class(cx)` and renders `<html class=(theme)>` directly — the correct class is present in the very first byte of the response, so there is no flash of the wrong theme and no bootstrap script is needed at all. For a first-time visitor with no cookie yet, `assets/styles.css` adds `@media (prefers-color-scheme: dark) { :root:not(.light) { ... } }` (the same dark values `.dark` already carries), so the OS preference still applies with zero JS or server involvement; the `:not(.light)` guard means an explicit `light` cookie can override even an OS-dark preference. The toggle button's click handler flips `document.documentElement.classList` immediately for instant feedback, then `POST`s the new value so it persists server-side for the next load. Sending the *new* value explicitly (computed from the DOM's current class) rather than asking the server to "toggle" blindly avoids a real edge case: a stateless server-side toggle can't distinguish "no cookie yet" from "was light", so a viewer whose page is currently dark via the OS-preference media query could see their first click appear to do nothing.

**Status colors also had to become theme-aware.** Discovered mid-implementation (not in the original plan): `full_style_for_color`/`border_style_for_color`/`text_style_for_color`/`chip_style` (`src/web.rs`) emitted hardcoded light-mode hex values as inline styles. Once the toggle could actually produce a dark page, every failing/stale/banded panel and every summary chip would render with the same pale light-mode tints regardless of theme. Fixed by moving those hex values into `--status-{red,yellow,green}-{border,bg,fg,text,chip-fg}` custom properties in `assets/styles.css` (light values in `:root`, dark overrides duplicated into both the `prefers-color-scheme` media query and `.dark`) and having the four functions emit `var(--status-*)` instead of literal hex. This keeps the existing inline-style architecture intact — `var()` inside an inline `style` still resolves against the live cascade, so it wasn't necessary to switch to Tailwind `dark:` utility classes (which would have required dropping `card`'s own default classes to avoid the specificity collision these functions were already written to avoid). `--status-green-bg`/`--status-green-fg` simply alias `var(--background)`/`var(--foreground)` rather than defining their own dark values, matching the original intent (a healthy banded panel already just used the page's own neutral surface). History-bar segment coloring (`Panel::segment_class`, plain Tailwind `bg-red-500`/`bg-amber-400`/`bg-emerald-500`/`bg-slate-200` classes) was deliberately left alone — out of scope for this fix, a smaller residual inconsistency, and not what was flagged.

**Border-embedded title: a positioned label over the card, not a `card.rs` change.** `panels_grid` stops calling `card_header`/`card_title` and instead wraps each card in a `relative`-positioned container with a small `<span>` absolutely positioned over the card's own top border (`top: -0.55em`, `left: 1rem`), padded left/right so the border line appears to break around the text — the standard "notched border" technique (the same one a `<fieldset><legend>` produces natively, done here with `position` instead since the panel card isn't a `<fieldset>`). The span's background must match whatever the card itself is currently rendered with, or the notch won't blend in:
  - A solo single-source/main-only card can carry a status color (`Panel::status_style()` — border, tinted background, and text color together); the title span reuses that exact same inline style string, so its cutout background always matches the card's current tint.
  - A multi-section (`main`+`secondary`/`table`) card's own background is always neutral (spec: web-ui — group panes card border reflects the worst member); its title span therefore only needs the neutral `bg-background` class, no per-status override.
  An untitled generalized pane (no `title`, no `main`) renders no span at all, matching "no header text" from before this change.

**Density: edit the vendored `card.rs`'s own classes.** Since `card` has exactly one consumer in this codebase, the padding/gap reduction is made once, in `card.rs`'s `CARD`/`card_header`/`card_content`/`card_footer` class constants, rather than trying to override them per call site. Overriding via an appended `class` string was rejected for the same reason `Panel::status_style()` already uses inline styles instead of classes for color: two conflicting utility classes (the vendored `px-6` and a project override like `px-4`) have identical specificity, and which one wins depends on Tailwind's generated stylesheet order, not source order in the markup — not a reliable way to guarantee the denser value applies. Grid gap and value-text-size reductions live in `web.rs`'s own non-conflicting classes (`gap-4`→`gap-3`, `text-3xl`→`text-2xl`, etc.), which have no such collision since nothing else sets them.

**Responsive grid: a named class + a `!important` narrow-viewport override, not Tailwind breakpoint classes.** The grid's column count is a runtime value (`grid.columns`, 1–6, from the user's config), so it must stay driven by an inline `grid-template-columns` — Tailwind can't generate a class for an arbitrary runtime column count it never sees at build/scan time (this inline-style-for-dynamic-values approach is already what the code does today). To make it responsive, the grid container gets a stable class (`bd-panel-grid`) and each cell/slot wrapper gets a stable class (`bd-panel-cell`); a small `<style>` block (alongside the existing one already in `dashboard()`'s `<head>`) adds:
  ```css
  @media (max-width: 640px) {
    .bd-panel-grid { grid-template-columns: 1fr !important; }
    .bd-panel-cell { grid-column: auto !important; grid-row: auto !important; }
  }
  ```
  `!important` is necessary and scoped narrowly (one media query, two classes) because inline `style` attributes otherwise always beat an external/embedded stylesheet rule regardless of source order. Below 640px, cells simply stack in DOM order (already row-major, top-to-bottom/left-to-right per the layout's own declaration order), which is a sensible reading order without any explicit placement. A `<meta name="viewport" content="width=device-width, initial-scale=1">` tag is added to `<head>` alongside this, since without it mobile browsers render the page at a virtual desktop width and then scale it down, which defeats the media query entirely (it would never see a viewport narrower than ~980px).

## Risks / Trade-offs

- [`!important` in the responsive override] Could bite a future developer who adds a third breakpoint or forgets it's there → scoped to exactly two classes in one media query, and called out by name in the `web-ui` spec's own "Responsive layout for small viewports" requirement plus a code comment at the `<style>` block.
- [Editing a vendored component] `card.rs`'s content hash in `components.toml` will no longer match the registry's version, so a future `topcoat ui update` (if ever run) would show it as locally modified → expected and desired under the vendoring model (the whole point of vendoring is that the file becomes project-owned); no action needed unless someone explicitly wants to pull upstream `card` changes later, at which point they'd need to re-apply this project's padding tweaks.
- [Title-span background drift] If a future change adds a new panel background treatment without updating the title span's matching style, the notch could show a mismatched patch → both call sites (solo-panel branch, combined-card branch) compute the span's background from the exact same style value already used for the card itself, not a separately maintained copy, so there's nothing to drift out of sync as long as that convention is kept.
- [Duplicated dark token values] The dark `--status-*`/base values are declared twice (the `prefers-color-scheme` media query and `.dark`), since plain CSS has no mixin to share them → both blocks carry an explicit comment pointing at each other; a follow-up that wants a single source of truth would need a preprocessor or a build step this project doesn't otherwise have.
- [History-bar segments stayed hex] `Panel::segment_class`'s Tailwind color classes are unchanged and don't have dark-specific variants → smaller, less jarring than the full-panel tints were (vivid mid-tone colors on small segments), and out of scope for what was actually flagged; a follow-up could add `dark:` variants there if it matters in practice.

## Migration Plan

1. Add `.cookies()` to the router builder, `POST /api/theme`, `theme_class(cx)`, the toggle button + script, and the `prefers-color-scheme` media query; no data migration, purely additive route/markup/CSS.
2. Move status colors to `--status-*` tokens and update the four color functions to reference them.
3. Rework `panels_grid`'s two card-rendering branches to use the border-title span instead of `card_header`/`card_title`, reusing the density and responsive-class changes from steps 4–5 at the same time (all three touch the same markup).
4. Reduce `card.rs`'s padding/gap constants and `web.rs`'s own spacing/type-scale classes.
5. Add `bd-panel-grid`/`bd-panel-cell` classes, the narrow-viewport `<style>` override, and the viewport meta tag.
6. Verification: integration tests cover the cookie round-trip (`POST /api/theme` → `Set-Cookie` → next `GET` renders the right class), the toggle button/viewport-meta/`bd-panel-grid`/`bd-panel-cell` markup, the border-title span (present, absent when untitled), and that no previously-shown panel content disappeared under the denser spacing. None of this is a substitute for actually looking at it in a browser across viewport widths and both themes — that manual pass has not been done in this environment (no browser available); see tasks.md for exactly what was and wasn't checked.

No rollback complexity: everything here is additive markup/CSS/route with no schema or data implications; reverting the commit fully restores prior behavior.
